Why I Built Visor

By Abdullah • 4 min read • September 2026

I was looking for a way to automate actions on a boring blue site.

I started by looking into browsers with agents to help do the actions. Quickly, I realized they take forever to figure out the path to perform the action required, or they are quite expensive due to taking many screenshots and navigating without memory.

I tried Comet at the start, which works extremely well. But you run out of usage quickly, and every time you ask for the same action it re-figures everything out from scratch. Plus, it is closed source (no changing of memory or method).

I then figured: what is the next best thing?

Searching for a bit, I found BrowserOS. Basically the dream: open source and has the same functionality, but now with skills such that it remembers the exact workflow. Still, since it operated on the DOM, it breaks quite a bunch and the agent still had to write a program every time for the same task. It was painfully slow and gets expensive when running on OpenRouter with lots of requests.

Relying on the DOM is a real issue for sites that actively fight agents. They can anonymize the elements, scramble classes, or make it very hard to figure out the needed element.

Eventually I figured: why not reduce the need for screenshots or even sending them as a request at all, and avoid DOMs as much as possible while striking a happy middle ground?

This is precisely why I made Visor.

A Middle Ground: Visual Without The Costs

Visor gives the text-based LLM access to visual elements without sending screenshots over the wire.

Instead of burning cloud vision tokens on every step, it runs a tiny OCR model locally. The model pinpoints the location of specific text like "Follow" or "Connect", and clicks it directly. No DOM manipulation required, and no fighting obfuscated code.

How It Works in Practice

1. Deterministic Most of the Time

Most browser agents ask an AI model what to do on every single click. That is why they are slow and expensive.

Visor flips this around:

  • It runs fast, predictable code by default.
  • It clicks what it sees, then checks for clear completion criteria to confirm the action actually worked (like verifying a button changed to "Pending").
  • The AI is not driving every second; it is only called in when something unexpected breaks.
from visor.core import runner

# Run deterministic visual steps across targets
runner.run_flow(
    flow_fn=connect_to_profile,
    targets="targets.csv",
    max_retries=3
)

2. A Memory That Actually Learns

Websites change all the time. A button gets renamed, an item moves into a dropdown, or a layout shifts.

When Visor runs into an unknown state, it signals AGENT_NEEDED:

  1. It pauses cleanly and saves what went wrong to a local failure log.
  2. An agent inspects the failure and teaches Visor what to do instead (for example: "if the button is missing, click the dropdown menu first").
  3. Visor saves that lesson permanently into its strategy map (tree.json).

Once Visor learns a fix, it repeats it on future runs without needing the agent again.

3. Stepping in When It Truly Matters

If an issue is too complicated or hits a hard security wall (like a captcha or two-factor prompt), Visor triggers a HUMAN_HANDSHAKE. It pauses, lets you get your hands dirty to solve the block yourself, and continues right where it left off once you are clear.

Hard-Won Lessons

Getting this working smoothly took plenty of trial and error. Some general patterns came up repeatedly:

  • Text Quirks: Small icons right next to text can sometimes confuse reading (like an icon right next to a label). Simple substring matching keeps things flexible.
  • Ambiguous Elements: Complex pages often have duplicate buttons in sidebars or recommended feeds. Giving the bot general boundaries keeps it focused on the main area.
  • Timing: Dropdowns and menus need a brief moment to animate open. Giving elements a split second to settle prevents false alarms.

What Is Next

Visor started as a tool to solve my own immediate headache, but there is still plenty to explore:

  • Adding native pagination managers so scrolling through large lists is completely handled under the hood.
  • Exploring local small language models (SLMs) to handle the on-call healing step entirely on-device with zero cloud dependencies.
  • Better hybrid fallback modes when a site actually has clean semantic markup worth reading.

Current State

For my usage, it works reliably. It gives me minimal friction when I ask it to navigate sites I do not want to waste time on or handle repetitive tasks I would otherwise dread.

Also, I am not fully sure of the current state of the whole ecosystem, but as far as I've tried, I couldn't find something better for my use case.
